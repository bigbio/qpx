# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **MuData reports cells with more than one intensity** — values that land in one matrix cell, such as two features of one precursor in one run, were summed without a trace: 14,020 of the 196,004 PXD001819 precursor cells (7.2%) receive more than one MaxQuant feature, 9,862 of them an MS/MS and a match-between-runs feature. `build_mudata(duplicates=...)` now takes `"sum"` (the default, as before) or `"mean"`; each modality's `uns["qpx_duplicates"]` records the aggregation and the number of such cells, and the build logs a warning when there are any. Values are unchanged by default.

### Changed

- **Peptide and protein abundance helpers are faster** — `Dataset.intensity()`, `Dataset.design_matrix()`, `PeptideView.intensity()`, `ProteinView.intensity()` and `Feature.for_quantification()` unnested `run.samples` and the feature intensities inside one `FROM` list, so DuckDB planned a cross product of features and runs at peptide level and joined every channel of a TMT feature to every channel of its run before matching the label; at protein level every pg row was resolved against every member run of its `grouped_runs`. Both lists are now unnested on their own and joined on run and label, and each distinct `grouped_runs` set is resolved to its samples once. On 405 label-free runs (2.94 million features) `intensity("peptide")` takes 0.37 s instead of 33.1 s. On fractionated TMT16 (12 runs, 240,000 features) it takes 0.59 s instead of 35.3 s, and `PeptideView.intensity()` and `Feature.for_quantification()` finish in 0.6 s where they ran out of a 5 GB temp directory. `ProteinView.intensity()` on 1.28 million fractionated TMT16 pg rows takes 0.8 s instead of 19.7 s. The worked example in [Data Model](docs/spec/data-model.md#label-channel-sample-resolution) resolves each `grouped_runs` set once in the same way. Output is unchanged.
- **BREAKING — MuData `proteins` obs column `run_file_name` is now `grouped_runs`** — protein observations are quantification units (see *Fixed*), so when `obs` is expanded over channels its run column names the unit's runs. The converters always write the expanded form, so every converter-written `.h5mu` has the new column, unfractionated ones included: on DIA-NN PXD036609 the protein observation names and values are the same as before and only the column name differs (and the decoys are gone, see *Fixed*). Code that reads `mdata["proteins"].obs["run_file_name"]` must read `grouped_runs`; precursor observations keep `run_file_name`.

### Fixed

- **MuData protein observations are quantification units** — the `proteins` modality exploded `grouped_runs` into one observation per raw file, each holding a copy of its unit's value, so a fractionated design counted every protein-group quantity once per fraction: on the OpenMS BSA fractions (3 samples × 2 fractions) the matrix summed to 2.0 times the pg total, on one TMT10 plex in 3 fractions to 3.0 times, and the two fractions of a SILAC mixture were identical observations. Each quantification unit and label is now one observation, named by its member runs sorted and joined by `;` (an unfractionated unit keeps its run name). The sample is resolved through any member run, `run_accession`, `fraction` and `instrument` are joined over the members, and replicate numbers on which the members disagree are left empty. The observations of fractionated designs change, and the obs column is renamed (see *Changed*). See [MuData](docs/spec/anndata.md#mudata-h5mu).
- **MuData leaves out decoys** — the precursor and protein matrices kept decoy precursors and protein groups with nothing in `var` to tell them apart, although [Protein Group View](docs/spec/pg.md) requires consumers to filter on `is_decoy`: the PXD036609 (DIA-NN) h5mu carried 181 decoy protein groups with 2,307 values and 184 decoy precursors, and PXD001819 (MaxQuant) 11 `REV__` protein groups and 14 decoy precursors. They are now left out unless `build_mudata(include_decoys=True)` keeps them, flagged in a boolean `var["is_decoy"]`; `uns["qpx_include_decoys"]` records the choice. The `.h5mu` written by the converters no longer contains decoys.

## [1.2.0] - 2026-10-30

### Added

- **Competing interpretations and sequence edits** — the optional `modification_candidates` column of the `psm` and `feature` views lists every modification considered at each position, the one the peptidoform places (`assigned`) and those it competes with, each with its probability given the identification: localization alternatives (a phosphate on S4 or T5), identity alternatives (acetyl or trimethyl on one Lys) and single-residue substitutions of the same mass. Mutually exclusive candidates share an `alternative_group`, whose probabilities sum to at most 1; candidates that co-occur (a SILAC label and an acetyl) do not sum. A new `sequence_edit` struct records changes relative to a reference protein (substitutions, multi-residue replacements, deletions, insertions) in `pepmap.sequence_edits` and `proteoform.edits`. Strict validation checks candidate probabilities per alternative group (allowing a sum up to 0.01 above 1, since producers such as MaxQuant round them), edit spans, and that the edits of one sequence are ordered and do not overlap; a nested field of the wrong type is reported as a type mismatch instead of stopping validation. A sequence edit that changes nothing (`reference` equals `alternative`) fails strict validation. The specification now states how feature candidates combine their identifications, the coordinates, target residue, direction and `assigned` of substitution candidates, and the insertion convention against VCF. The MaxQuant converter now keeps every residue of `Phospho (STY) Probabilities` as a candidate; the unassigned ones were dropped before. See [Competing interpretations](docs/spec/modifications.md#competing-interpretations) and [Sequence Edits](docs/spec/sequence-edits.md).
- **`site` and `proteoform` views** — `{PREFIX}.site.parquet` reports protein modification-site claims, one row per (protein, residue, modification, runs): `site_qvalue` controls error over those claims (counted per row, not per PSM), `modified_probability` is the probability that the residue carries some modification (not stoichiometry), and `evidence_fraction` with `alternatives` is the share of the residue's modification evidence for each candidate modification, since near-isobaric modifications such as acetyl and trimethyl often cannot be told apart; the id keys on the modification name, so modifications of equal mass are distinct rows. `{PREFIX}.proteoform.parquet` reports, per protein family, the canonical entry and each isoform, sequence variant and processed chain the evidence supports, with a member-level `proteoform_qvalue` (null when only PSM-level estimates exist), flattened per label like `pg` with a `pg_id` per label. Strict validation checks that q-values, probabilities and fractions are finite and in [0, 1], that a residue's fractions sum to 1, and that `pg_id` links resolve to a pg row of the same label and runs that holds the site's protein or the proteoform's family. Both have writers (`SiteWriter`, `ProteoformWriter`), structures with filters (`by_protein`, `by_modification`, `confident`; `by_family`, `by_kind`, `confident`), `Dataset` discovery and `Dataset.save_structure` support, and `qpxc transform normalize-accessions` rewrites their accessions (`protein_accession` and `family` of site, `family` and `accession` of proteoform) along with feature and pg, so their `pg_id` links still hold. See [Modification Sites](docs/spec/site.md) and [Proteoforms](docs/spec/proteoform.md).

### Changed

- **Specification version 1.2** — files are written with `qpx_version` 1.2. It adds the `site` and `proteoform` views, the optional `modification_candidates` column of `psm` and `feature` and the optional `sequence_edits` column of `pepmap`, and lets run, mz and PSM files leave out the columns the spec does not require; nothing is removed or retyped, so 1.1 files are valid 1.2 files (see [Versioning](docs/spec/versioning.md#changelog)).
- **Feature writing is faster and uses less memory** — the feature writer copied every row's `cv_params` into Python even when no row carried a producer-supplied `feature_id`, and counted every derived ID only to reword a duplicate-key error that the write path reports as a warning. On PXD056598 (DIA-NN, 5.29 million features) the feature step of `convert diann` takes 48.7 s and 8.6 GiB instead of 114.9 s and 19.0 GiB. Output is unchanged.
- **`convert diann` mz view is faster** — matched MS2 spectra are read from the MS-info tables in record batches with their peaks kept as float32 arrays, and the matched scans are collected from the feature file with Arrow kernels instead of Python loops. On four DIA runs (93,050 MS2 spectra) the mz step takes 5.5 s instead of 11.3 s, and collecting the matched scans takes 0.13 s instead of 4.05 s. Output is unchanged.
- **`convert openms-consensus` is faster** — provenance parsed each consensusXML header together with all its unassigned identifications; it now stops before them, and only the isobaric fallback, which needs the map labels, reads further. Feature IDs round their float32 identity fields per value instead of building an Arrow scalar per field, and unmodified peptides skip the modification parsing. Provenance for 26 quantms LFQ consensusXML files takes 2 s instead of 408 s; PXD044981 (DDA) converts in 60.7 s instead of 75–77 s, and PXD002099 with `--streaming` in 26.0 s instead of 29.8 s. Output is unchanged.
- **`convert diann` scan merging and `convert spectronaut` row building are faster** — with `--mzml-info-folder`, DIA-NN converted the whole feature table to pandas to fill the scans; only the five columns the merge reads go through pandas now. Spectronaut builds `pg_accessions` with the Arrow kernels of the DIA-NN converter (now shared in `converters/utils.py`) instead of one Python dict per accession, and its pg step reads rows from `to_dict("records")` instead of `iterrows`. The DIA-NN scan merge of 116,744 rows takes 0.34 s instead of 1.85 s; Spectronaut `pg_accessions` for 1 million rows takes 0.042 s instead of 1.47 s, and the pg rows for 200,000 report rows 1.76 s instead of 5.22 s. Output is unchanged.
- **`qpxc transform gene-map` streams the views** — it read the whole feature or pg view into one pandas DataFrame and wrote it back; it now annotates Parquet batches and writes them through the view's writer. On PXD056598 (5.29 million features) it takes 48.7 s and 1.75 GiB instead of 151.7 s and 70.4 GiB. An empty view is written as an empty file instead of failing. Output is otherwise unchanged.
- **SDRF channel relabelling is vectorised** — `convert openms` and `relabel_intensities_parquet` renamed each row's intensity labels in Python; the labels are now mapped once per distinct value with Arrow dictionary encoding. For 1 million rows with 16 channels this takes 1.15 s instead of 33.3 s. Output is unchanged.
- **`convert fragpipe` stops hiding failures** — when `psm.tsv` could not be loaded, the conversion logged a warning and wrote features without their PSM scan, PEP, m/z and decoy flag; it now fails. Rows of `psm.tsv`, `combined_ion.tsv` and `combined_protein.tsv` are still skipped for bad values, but only on value, type, key, index and arithmetic errors, as in `convert cdap`; any other error is raised.
- **An unloadable PSI-MS ontology stops the conversion** — score and field ontology entries and SDRF run terms use the PSI-MS ontology shipped with qpx. A failure to load it was swallowed, so `ontology.parquet` silently lost its PSI-MS accessions and versions; it now raises.
- **`convert diann` and `convert maxquant` SDRF step** — any error while writing `sample` and `run` from the SDRF was logged and the two views were dropped. As in `convert spectronaut`, only value, key, OS and type errors are now treated as an incomplete SDRF; other errors stop the conversion.
- **`--enrich-pride` warns only for PRIDE lookup and file errors** — any error while fetching PRIDE metadata or writing it to `dataset.parquet` was printed as a warning. Network, HTTP, OS and value errors still are, since the enrichment is best-effort; other errors stop the conversion.
- **`mz.ion_injection_time` is nullable** — `convert diann`, whose MS-info tables carry no injection time, and `qpxc convert mz` for scans without `MS:1000927` wrote 0. Both now write null, and the mz schema no longer requires a value.
- **`qpxc transform quantify` reads only the columns it uses** — it loaded every column of the feature view into pandas and expanded each row's intensity list in Python. It now reads the four columns it needs, flattens the intensities with Arrow kernels and resolves each distinct run and label to its sample once. On PXD056598 (5.29 million features) the peptide table is built in 1.2 s and 1.5 GiB instead of 53.4 s and 45.1 GiB. Output is unchanged.
- **The conversion summary and `Dataset.link_feature_pg()` are faster** — the feature→pg softlink joined feature and pg rows on protein-group membership alone and then tested each pair's run with `list_contains`; `grouped_runs` is now unnested so membership, run and label are all join keys. The conversion summary also ran the join once for each of its three feature→pg counts; they now come from one pass. On PDC000116 (CDAP TMT10, 2.54 million features, 10.2 million pg rows) the conversion summary takes 5 s instead of 139 s. Output is unchanged.
- **`qpxc transform normalize-accessions` is faster and keeps the QPX encoding** — it read each view whole, mapped every row's accessions in Python and wrote the file with pyarrow's default encoding even when no accession changed, so a 434 MB feature view came back as 617 MB. Each distinct accession is now mapped once; a view with nothing to change is copied as is, and a changed view is rewritten in bounded batches with the encoding of the other QPX writers and a new footer `uuid`. The pg view also keeps the non-null `anchor_protein` and `pg_accessions` fields it was declared with. On PXD056598 (5.29 million features) the reverse direction takes 25.0 s and 1.8 GiB instead of 40.9 s and 10.3 GiB, and an already-bare feature view takes 0.7 s instead of 37.2 s. Values are unchanged.
- **`convert cdap` parses each peptide once** — the PSM and feature steps parsed every row's peptide string and computed its precursor m/z again; the shared parser caches hold fewer entries than a study has distinct peptides (PDC000116: 226,199 peptides and 295,596 peptide–charge pairs over 3.44 million PSMs), so they missed on most rows. Each adapter now remembers the parsed peptide and m/z for the rest of the conversion. On PDC000116 the PSM step takes 103 s instead of 130 s and the feature step 151 s instead of 183 s. Output is unchanged.
- **Filling `feature.pg_positions` from a FASTA is faster** — `qpxc transform protein-properties` and `--fasta` on the converters built a Python tuple of accessions for every feature and rebuilt the whole column from Python lists. Each distinct sequence and protein group is now searched once and its positions are taken back to its rows with Arrow; values the producer recorded are carried over as they are. On PXD056598 (5.29 million features) filling the column takes 0.8 s instead of 10.4 s. Output is unchanged.
- **Deriving `feature_id`, `psm_id` and `pg_id` is faster** — each row's identity composite was encoded with `json.dumps`, which builds a new encoder on every call, after copying every list value; one shared encoder now encodes the values as they are. The hashed bytes, and so every id, are unchanged. Deriving the ids of the 5.29 million PXD056598 features takes 6.0 s instead of 9.2 s, and of the 10.1 million PDC000116 pg rows 17.9 s instead of 36.8 s.
- **`qpxc validate` reads each view in batches** — it loaded every column of a view into memory before checking it, so memory grew with the largest view. The checks that read one row at a time now count batch by batch, only the primary-key columns are held for the whole view, and the pg referential checks run as SQL on the view. Validating PDC000116 (CDAP TMT10) peaks at 2.6 GB instead of 8.4 GB, and PXD056598 at 1.6 GB instead of 5.6 GB. The reported issues are unchanged.
- **pg views are written without one Python dict per label** — `PgWriter` copied each protein-group record into one dict per label and then converted every row to Arrow; the records are now converted once and the label rows are taken from them with Arrow kernels, additional intensities filtered by label as before. The written files are unchanged, row groups included. On PDC000116 (CDAP TMT10, 10.1 million pg rows) the pg step takes 120 s instead of 193 s.
- **`qpxc validate` reads only the columns its checks use** — the row checks read the required columns and a few others, but every column of the view was decoded for them, the intensity lists included. Only those columns are read now. Validating the PXD004701 feature view (13.57 million rows) takes 3.5 s and 1.2 GiB instead of 19.2 s and 1.7 GiB. The reported issues are unchanged.
- **MuData is built faster and with less memory** — the precursor and protein queries expanded each feature's intensities and each protein group's `grouped_runs` with a lateral `UNNEST` join, which DuckDB plans as a join with the whole view; they now unnest in the select list. Building the precursor and protein modalities of PXD004701 (13.57 million features, 300 runs) takes 3.2 s and 1.7 GiB instead of 8.9 s and 3.8 GiB. Output is unchanged up to the last float32 digits of precursor intensities summed over duplicates, which already varied between runs.
- **`qpxc transform gene-map` resolves each protein group once** — it decoded every row's `pg_accessions` into Python and resolved its genes again, although rows share few protein groups, and the writer then decoded every row's identity fields only to keep the ids the rows already had. Each distinct protein group is now resolved once and its names are taken back to the rows with Arrow, and a batch whose rows all keep their ids is written without reading the identity fields. On PXD002395 (2.56 million features) the feature view is annotated in 3.7 s and 1.1 GiB instead of 21.0 s and 1.5 GiB. Output is unchanged.
- **MuData export no longer hides query errors** — label detection and the run metadata lookup treated any error as a missing view, so a feature or run view that failed to read gave a MuData with guessed labels or without sample metadata. They now check whether the view exists, and other errors are raised.
- **DuckDB thread and memory defaults** — without `--max-cpus`/`--max-memory` (or `--duckdb-threads`/`--duckdb-memory`, or the `duckdb_threads`/`duckdb_memory` arguments of `Dataset`, `Collection` and the adapters), qpx set 4 threads and a 16 GB memory limit (24 threads for `pdc2qpx`, 32 GB for `Collection`). It now uses one thread per CPU the process may run on and DuckDB's default limit of 80% of RAM. Both follow a container's CPU and memory limits, and the thread count also follows a taskset or SLURM/LSF cpuset, which DuckDB on its own ignores.

### Removed

- **Unused converter APIs** — `BaseConverter.write_ontology` and `write_score_ontology` (the orchestrators write `ontology.parquet`), `BaseWriter.overridden_id_count`, and the openms-consensus `consensus_psms_to_records` and `consensus_protein_groups_to_records`. Only tests called the two record functions, and the PSM one left out the converter's feature links, missed cleavages and peptide-level confidence; the tests now check the converter output. Four private copies of a file SHA-256 helper are merged into `qpx.core.files.sha256_file`.
- **No-op `convert diann` and `convert maxquant` options** — `convert diann --protein-file`, `--partitions`, `--batch-size` and `--standardized-intensities`, and `convert maxquant --protein-file` and `--standardized-intensities`, were accepted and ignored. They are removed, so passing one is now a usage error; workflows that pass them must drop them before upgrading.
- **Reading feature files whose intensities are keyed by `channel`** — this quantms.io layout (`intensities[].channel` next to `sample_accession`) predates QPX 1.0. The `Dataset`, `Feature` and MuData queries each probed for it and joined such files on `sample_accession`, and `qpxc transform quantify` read them with empty labels. `Feature.from_file` and `qpxc transform quantify` now raise `QpxVersionError`, and `Dataset` skips the feature view with a warning, as it does for a pre-1.1 pg file. Regenerate these files with qpx.
- **`--batch-size` of `convert cdap`, `convert fragpipe`, `convert maxquant` and `convert quantms-msstats`**, and the `batch_size` argument of their converter classes — each converter now uses a fixed batch size: the former CLI default, and 500,000 rows for `quantms-msstats`. On PXD003539, `quantms-msstats` peaked at 9.9 GiB with 10,000, 50,000 or 500,000 rows per batch, and the 500,000-row feature file is 15% smaller (223 MB instead of 262 MB).
- **`convert maxquant --fixed-mod-only`** — the flag dropped every evidence row whose `Modifications` value was neither `Unmodified` nor `Carbamidomethyl (C)`, a filter no other converter offers. Select peptidoforms from the feature view's `modifications` instead.
- **The `n_workers` argument of `MaxQuantConverter.convert`** — it overrode the DuckDB thread count that `MaxQuantConverter(max_cpus=...)` already sets, and `convert maxquant` passed `--max-cpus` to both.
- **`qpx.open()`**, deprecated since 0.5.0 — use `qpx.open_dataset()`.

### Fixed

- **`convert maxquant` missing m/z** — `feature.calculated_mz` and `psm.calculated_mz` were 0 when a row had no mass or charge, and `feature.observed_mz` was 0 without an `m/z` value. They are now null, as the schema allows; `psm.observed_mz` is required and stays 0.
- **`convert fragpipe` missing m/z** — `feature.calculated_mz` and `feature.observed_mz` were 0 when neither `psm.tsv` nor the ion table had a value, and `psm.calculated_mz` was 0 without `Calculated M/Z`. They are now null. `compensation_voltage` stays 0 for non-FAIMS units because it is part of the feature identity.
- **`convert diann` `calculated_mz` of an unknown modification** — a precursor whose mass could not be computed got `calculated_mz = 0`; it is now null, like `observed_mz` ([#244](https://github.com/bigbio/qpx/issues/244)).
- **`convert spectronaut` missing m/z** — `calculated_mz` was 0 for a precursor whose mass could not be computed, and `observed_mz` was 0 when the report had no precursor m/z column or value. Both are now null, as in `convert diann` ([#244](https://github.com/bigbio/qpx/issues/244)).
- **`Dataset.design_matrix(value_col=...)`** — the parameter was documented as selecting the intensity column to pivot but was ignored; `intensity` was always used. Any other value now raises `ValueError`.
- **`qpxc info schema --structure` accepts every structure** — the choices were a hand-kept list without `pepmap`; they now come from the `Dataset` registry, like `qpxc validate` and `qpxc query` ([#289](https://github.com/bigbio/qpx/issues/289)).
- **`qpxc transform quantify` skips features without an anchor protein** — a feature whose peptide is shared by several protein groups has a null `anchor_protein`; its intensities were quantified under a protein named `None`. These features are now left out.
- **Works with DuckDB 2.0; DuckDB 1.5.0 or later is required** ([#356](https://github.com/bigbio/qpx/issues/356)) — DuckDB 2.0 removed `fetch_arrow_table()` and `fetch_record_batch()` from connections and rejects the `x -> ...` lambda syntax, so `qpxc validate`, the converters and the MuData export failed with it. qpx now reads Arrow through relations with `to_arrow_table()` and `to_arrow_reader()`, which stream instead of materializing the whole result as DuckDB 2.0 does for `execute()`, writes lambdas as `lambda x: ...`, and reads every `execute()` result to the end, since DuckDB 2.0 refuses relation work on a connection with an unread result. The minimum DuckDB version rises from 1.3.0 to 1.5.0, the first release with these method names on both connections and relations. `QueryResult.to_df()`, `to_arrow()` and `to_polars()` now read through a relation too, so they no longer warn about an extra copy with DuckDB 2.0 and can be called more than once on the same result.
- **Run, mz and PSM views may leave out the columns the spec does not require** ([#356](https://github.com/bigbio/qpx/issues/356)) — the run spec marks `file_name`, `fraction`, `instrument`, `enzymes`, `dissociation_method`, `acquisition_method`, `additional_terms` and `modification_parameters` as not required, but validation reported each missing one as an error, even with `strict=False`. They are now optional columns that a run file may omit. MuData export and `Feature.for_quantification()` read an absent `fraction` or `instrument` as null; MuData export would otherwise have dropped all run and sample metadata from `obs`. The spec now explains the *Required* column (yes, no, optional), and the feature, PSM and sample tables mark as optional the 13 columns their schemas already allowed to be absent. Six mz columns (`run_file_name`, `scan`, `inverse_ion_mobility`, `ion_injection_time`, `precursors`, `cv_params`) and seven PSM columns (`mz_array`, `intensity_array`, `charge_array`, `ion_type_array`, `ion_mobility_array`, `ion_mobility`, `cross_links`) are optional too, so a PSM view can leave the peak arrays to the mz view ([#355](https://github.com/bigbio/qpx/issues/355)) and files without ion mobility or cross-links need no all-null columns.
- **`convert openms` annotates the scores in `additional_scores`** — the converter looked for each score's name under `name`, but the `score` struct names it `score_name`, so it found none and wrote no ontology entry for any of them. Scores with a PSI-MS term now get one, as in the other converters.
- **`qpxc info` counts every file of a view** — the dataset summary read the row count of the first file only, so a view split over several files (`a.feature.parquet`, `b.feature.parquet`) or partitions was undercounted. It now counts the rows the view itself returns.
- **`qpxc transform normalize-accessions --output` help** — it said the views were overwritten in place when `--output` is omitted; the command requires `--output` or `--in-place`, and the help now says so.

## [1.1.0 – 1.1.6] - 2026-10-13

### Changed

- **Unreadable SDRF and `proteinGroups.txt` inputs stop the conversion** — `convert diann`, `convert spectronaut` and `convert openms-consensus` ignored an SDRF they could not read for the enzyme, and `convert maxquant` ignored a `--protein-groups-file` it could not parse or that had no `Protein IDs`/`Majority protein IDs` column. Each only logged the problem, so `missed_cleavages` was null or features lost their protein-group q-values and genes. These inputs now raise an error.
- **`mz.scan` is a `list<int32>`**, like `psm.scan` and `feature.scan`, so mz spectra join PSM/feature rows on `run_file_name` + `scan` for every native-ID format (see [Scan Numbers](docs/spec/scan.md)). `qpxc convert mz` wrote a single integer parsed from `scan=` and left it null for other formats, such as tdf2mzml's `index=N`. mz files written with the old `int32` column are read as one-element lists, so they still load, join and validate.
- **OpenMS feature protein attribution for shared peptides** — releases up to 1.1.3 assigned every feature to the protein group of its *first* protein evidence, an order that carries no meaning, and set `unique` from that group's size. A peptide shared by two groups was therefore attributed to one of them arbitrarily and often reported `unique = true`. Features now resolve their group from the full evidence set and the originating identification; when the evidence spans more than one inferred group, `anchor_protein`, `pg_accessions`, `unique`, `pg_global_qvalue` and `gg_*` are null and the feature's intensities are kept. `pg` is unaffected, since protein intensities are built from unique peptides only. On PXD000612 (DDA LFQ, 231 runs) this nulls the group on 255,416 of 3,956,057 features (6.5%, 9,331 peptidoforms, 15% of feature intensity), 8,829 of which 1.1.3 had marked unique. **OpenMS datasets converted with earlier releases over-report `unique` and carry arbitrary groups on shared peptides; reconvert before relying on feature-level protein attribution.**
- **MuData stack is core**: `mudata`, `anndata`, and `scipy` are required dependencies (no longer an optional extra). Use bare `pip install qpx`.
- **`quantify` extra**: now `mokume[directlfq]>=0.1.0` (DirectLFQ via mokume's optional extra).
- **Convert warnings go to stderr** ([#346](https://github.com/bigbio/qpx/pull/346)) — the MuData and `--fasta` warnings moved from stdout to stderr. All `qpxc convert` CLI warnings now start with `WARNING:`.
- **`convert diann` protein-group step is vectorised** ([#291](https://github.com/bigbio/qpx/issues/291)) — `pg` was built with a Python loop over every (protein group, run) group; it is now aggregated with grouped pandas operations, and feature `pg_accessions` is split with Arrow kernels instead of one Python dict per accession. Output is unchanged. On PXD056832 (368,251 pg rows) the pg step takes 15.8 s instead of 193.7 s; the feature `pg_accessions` build for its 1.8 million features takes 0.03 s instead of 2.3 s.

### Removed

### Fixed

- **`convert diann` protein groups: no protein q-value cut, decoy groups and `PG.PEP`** ([#342](https://github.com/bigbio/qpx/issues/342)) — `--qvalue-threshold` also dropped protein groups whose `Global.PG.Q.Value` (else `PG.Q.Value`) exceeded it. quantmsdiann passes its 5% precursor cutoff, so `pg` stopped at a protein-group q-value of 0.05 while `feature` kept those groups (1,424 of 8,805 groups on PXD040205). The threshold now selects precursors by `Q.Value` in both views, and protein-group q-values are only carried; like the feature view, the pg view needs `Q.Value` when a threshold is given. `PG.PEP` is written to `additional_scores` as `pg_pep`. With `--report-decoys`, DIA-NN reports a decoy precursor (`Decoy = 1`) under its target's protein group; these rows were merged into the target group, or written as a target group when no target matched. They now form their own groups with `DECOY_` accessions, `is_decoy = true` and their own q-values and PEP. Decoy features carry the same `DECOY_` accessions in `pg_accessions` and `anchor_protein`, so they link to the decoy group, not to the target group. Consumers must filter on `is_decoy`.
- **`convert openms-consensus` decoy flag for peptides matching target and decoy proteins** ([#342](https://github.com/bigbio/qpx/issues/342)) — a hit with `target_decoy = target+decoy` also matches a target protein, and OpenMS counts it as a target, but `psm.is_decoy` and `feature.is_decoy` were `true` because the converter only checked that the value contained "decoy". On PXD002099 this flagged 163 PSMs and 74 features whose protein accessions were all targets. Only `decoy` now marks a decoy match. True decoy PSMs keep their `DECOY_` accessions, and decoy protein groups in the input are written to `pg` with `is_decoy = true`. The PG spec now states that decoy rows may be present and that consumers filter on `is_decoy`.
- **`convert openms-consensus` pg rows only where a protein group has evidence** ([#280](https://github.com/bigbio/qpx/issues/280)) — a group's identification evidence in a quantification unit is now a PSM of the group from a raw file of that unit, with the run resolved as in `psm`. Before, a PSM counted for every run its consensus feature was quantified in, so a unit reached only through a transferred (match-between-runs) feature got a row for every label, with null `intensity` where the group had no unique-peptide signal. A group with no attributable run (a protein that no PSM references, or only PSMs whose run cannot be resolved) got a null row in every unit. In a unit without a PSM of the group, rows are now written only for labels with a measured quantity, and a group without evidence gets no row. On 26 quantms LFQ consensusXML files with their SDRF, this removes 39,985 of 2,498,927 pg rows, all with null `intensity` in units without a PSM of the group. All other rows are unchanged, including 279,766 rows quantified through transferred features. The PG spec now defines identification evidence in a unit and the one-row-per-label rule.
- **`convert openms-consensus` provenance from the consensusXML header** ([#346](https://github.com/bigbio/qpx/pull/346)) — provenance now lists the tools recorded in the file: search engine, rescoring tool, and each `<dataProcessing>` tool with its version. A tool with several processing actions, such as ProteomicsLFQ, gets one step per action. The quantms-rescoring label for merged search engines (`quantms-consensus-rescoring`, earlier `quantms-rescoring`) is a rescoring step, not a search engine; the file does not name the merged engines. For files with `<dataProcessing>` entries, dataset `software_name` changes from `OpenMS/ProteomicsLFQ` or `OpenMS/IsobaricWorkflow` to `OpenMS`. Files without them keep `OpenMS/ProteomicsLFQ` or `OpenMS/IsobaricWorkflow`. `software_version` is the version that the tools record. It is null when the versions differ or when no version is recorded.
- **SDRF modification parameter columns without NT or AC** ([#346](https://github.com/bigbio/qpx/pull/346)) — `comment[modification parameters]` columns whose value has neither `NT=` nor `AC=` (for example "not available") are skipped, so they no longer produce empty `run.modification_parameters` entries. With peptide-level FDR (`Percolator:peptide_level_fdrs`) they are the peptide's: `feature.peptide_qvalue`/`posterior_error_probability` take the peptide's best PSM, `psm.posterior_error_probability` stays null, the PSM carries `peptide_qvalue` in `additional_scores`, and Percolator's 1.0 placeholders are not reported.

### Changed

- **Feature/PSM/PG primary key is now the derived id** (`feature_id` / `psm_id` / `pg_id`) instead of the composite tuple; the previous composite is retained as the footer-declared `identity_composite` the id is derived from
- **Deterministic ids across write paths**: the id is now derived from the **persisted (Arrow-cast) values** in a single place, so `write_batch`, `write_table`, and `write_dataframe` produce identical ids for the same row (previously a float32 field such as `rt` could hash differently on the record vs table path). The `write_table`/`write_dataframe` paths derive the id before the non-nullable cast, so a frame/table without a precomputed id is accepted
- **Injective identity encoding**: `canonical()` uses JSON (quoted/escaped) instead of a delimiter join, so composites whose list elements or fields contain the delimiters (e.g. run names with commas) can no longer alias to the same id. Ordered list fields such as multi-component `scan` identifiers retain their order; only set-valued `grouped_runs` is canonicalized without regard to order
- **Referential validation** also flags reciprocal feature↔psm desync (an edge present one way but contradicted by the other), as a warning, only where the opposite direction is populated
- **OpenMS consensus identity** retains every spectrum reference associated with a run and the parent `consensus_rt`, preventing distinct ConsensusFeatures from collapsing onto the same derived `feature_id`
- **BREAKING — pg view flattened**: the `pg` view changes from one row per `(anchor_protein, grouped_runs)` carrying a nested `intensities: list<{label, intensity}>` column to **one row per label** with scalar `label` + `intensity` columns (identification-only groups become a single row with null `label`/`intensity`). Converters still build the natural per-group `intensities` list; the writer materializes the flat layout. Regenerate pg files
- **De-novo relaxation**: `feature.is_decoy`, `feature.anchor_protein`, and `psm.is_decoy` are now **nullable** (previously required) so de-novo / no-inference records are representable — consumers must no longer assume these are non-null
- **BREAKING — Feature/PSM identity composites** (format 1.1, issue #217): the
  schema-default Feature composite changes from `[sequence, charge,
  run_file_name, anchor_protein]` to `[peptidoform, charge, run_file_name, rt]`;
  the PSM composite changes from `[sequence, charge, run_file_name, scan]` to
  `[peptidoform, charge, run_file_name, scan]`. Measured across ~13M real rows,
  `anchor_protein` is functionally redundant and apex `rt` distinguishes
  repeated peaks where the producer reports it. A converter may declare a
  different producer-specific Feature composite when its upstream entity uses
  other measured properties. The actual primary keys are the mandatory opaque
  ID columns described above. Regenerate Feature and PSM files.
- **Parquet output size**: writers now apply `BYTE_STREAM_SPLIT` encoding to high-entropy float columns (rt, rt_start/stop, predicted_rt, calculated/observed m/z, intensity arrays) and raise the ZSTD level to 9. Encoding-only and fully lossless — no schema change; output reads unchanged with pyarrow and DuckDB. Measured ~16% smaller on a 14 GB feature.parquet.

### Deprecated

- **`qpxc convert openms` (the OpenMS `-out_qpx` parquet path)**: deprecated in favour of `qpxc convert openms-consensus`. OpenMS `-out_qpx` mis-assigns **every** PSM's `run_file_name` to the first run (the per-PSM `map_index` is dropped; OpenMS#9872) and emits duplicate PSMs (one feature-attached + one unassigned; OpenMS#9871) — so on any multi-run / multi-fraction / multi-replicate design ~half the PSMs carry the wrong run. `qpxc convert openms-consensus` reads the consensusXML directly and resolves the correct run per PSM (via `map_index`/`id_merge_index`/feature-element runs), so it does not have these defects. ### Fixed

- **DIA-NN q-value handling — feature/pg consistency, filtering is opt-in** (bigbio/qpx#241): the DIA-NN feature and pg views are now consistent and **neither filters by default**. `--qvalue-threshold` is opt-in (default unset): with no threshold the converter emits every feature and protein group the report contains, since DIA-NN already FDR-filters its main report and all per-row q-value columns (feature: `Q.Value`, `Global.Q.Value`, `PEP`, `Lib.Q.Value`, `Translated.Q.Value`; pg: `PG.Q.Value`, `Global.PG.Q.Value`, `Protein.Q.Value`, `Lib.PG.Q.Value`, `GG.Q.Value`) are carried through unconditionally for downstream filtering at any level. This resolves the earlier feature/pg inconsistency and count inflation by making both views as-reported rather than by forcing a pg filter. When `--qvalue-threshold` **is** given, each view filters at its own level — the feature view on precursor `Q.Value` and the pg view on `Global.PG.Q.Value` (falling back to `PG.Q.Value`). The Spectronaut converter's `--qvalue-threshold` is likewise opt-in.
- **DIA-NN empty channel columns**: reports whose `Channel`/`Label` column is entirely empty are treated as label-free, while partially missing multiplex channel identifiers remain invalid.
- **FragPipe Feature PSM enrichment**: `experiment_annotation.tsv`, explicit experiment mappings, or SDRF mappings now resolve each experiment to its exact raw run before attaching PSM metadata; multi-run experiments are left unenriched instead of borrowing one fraction's PSM.
- **Deterministic DIA-NN merged-group PG quantity**: when annotation noise merges protein-group rows that disagree on `PG.Quantity` / `PG.MaxLFQ`, the pg view now emits the max of the finite values (order-independent) instead of a row-order-dependent "first", and warns when the values actually disagree.
- **DIA-NN `observed_mz` NULL instead of 0.0 sentinel** (bigbio/qpx#244): a feature with no `Precursor.Mz` and no `ms_info` source now carries a truthful `NULL` observed m/z rather than a `0.0` that corrupts downstream mass-error / PPM math; report runs with no matching `*_ms_info.parquet` are warned about before being dropped.
- **Controlled unidentified Feature identity fallback**: an unidentified Feature (null `peptidoform`) with no producer id derives a candidate `feature_id` from the declared composite. The fallback is accepted with a warning only after full-file primary-key uniqueness succeeds; a collision remains a hard error. A producer-supplied id remains namespaced by run and preserved as a `provided_feature_id` cv_param.
- **openms-consensus isobaric detection**: real quantms `IsobaricWorkflow` output stamps TMT/iTRAQ consensusXML with `experiment_type="label-free"` while the maps still carry `tmt6plex_*`/`itraq*plex_*` labels. The converter now detects channels from the **map label** (not `experiment_type`), so real quantms TMT no longer collapses all reporter channels into a single `LFQ` label. Verified on real cluster output (PXD000001 TMT → TMT126–131; BSA/PXD002395 LFQ unchanged)
- **RT unit conversion**: DIA-NN and MaxQuant converters now correctly convert retention time from minutes to seconds in feature and PSM parquet output
- **Code quality**: Spectronaut converter refactored to reduce cyclomatic complexity, fix logging f-string interpolation, remove unused arguments, and eliminate duplicate code
- **CDAP label-free intensity label**: label-free `PrecursorArea` intensities are now emitted with the `"LFQ"` label (aligned with the FragPipe/MaxQuant converters) so downstream label-free consumers (mokume) recognize them as primary intensities
- **QPX TMT/iTRAQ channel labels**: OpenMS `-out_qpx` enrichment relabels feature/pg intensities from filenames/bare indices to plex-aware canonical reporter names; `run.samples[].label` is normalized to match — all from the shared sdrf-pipelines `channel_map` vocabulary
